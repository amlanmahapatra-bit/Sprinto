# Component Map: Sprinto Outreach Engine

Diagram: `docs/component_map.png`. Whiteboard photo: `docs/whiteboard_evidence_map.jpg`. Case brief: `docs/CASE_BRIEF.pdf`. This is the agreed architecture. Build each step as described, in this order. The case's 7 pipeline steps are rows 1–7; row 0 is the trigger, row G is the review gate (from the whiteboard), and row M is measurement. Don't add steps. In particular, there's **no self-learning loop** in this build.

| # | Stage | Owner (actor) | Step | What happens |
|---|-------|---------------|------|--------------|
| 0 | Trigger | Growth Lead (GL) | **GL starts a run** | GL pastes or uploads a list of domains, **or** clicks **Discover**: Google News RSS + Gemini Google-Search find recent Series A–C SaaS funding / compliance news and propose 10–20 domains (deduped against companies contacted in the last 90 days). GL ticks domains and clicks **Run**. Input is normalised (strip protocol/`www`, lowercase) and validated. From here on, no person is asked anything until Gate G. |
| 1 | Input | Scraper (code) | **Scrape the website** | For each domain: fetch the homepage, then discover and fetch up to 8 key pages (about, pricing, careers/jobs, security/trust, customers/case studies, press/blog). Discovery uses sitemap.xml + homepage links + common paths. Fetch chain: Jina Reader → plain fetch + Readability → Firecrawl (optional key). Also run DNS lookups (CNAME/A/MX/TXT) for cloud and tooling signals. Store markdown + hash per page in `pages`. Robots.txt respected; 10 s timeout per page. |
| 2 | AI | Gemini (extractor) | **Extract structured company data** | Gemini reads the pages and returns a strict JSON `CompanyFacts` (ICP_SPEC §4) using structured output. Every non-null field carries `quote` + `source_url`. Code then drops any field whose quote isn't found verbatim in that page. Result: facts + evidence rows, each criterion marked `found` / `not_found` / `unknown`. |
| 3 | Processing | Scorer (code) + Research agent (Gemini) | **Qualify against the ICP, with an agent loop** | Deterministic scorer applies hard gates and points from the active `icp_config` (ICP_SPEC §3) → `GO` / `NO_GO` / `RESEARCH_MORE`. On `RESEARCH_MORE`, the research agent picks the next action from allowed tools (`google_search`, `news_search`, `fetch_url`, `find_page`, `dns_lookup`) aimed at the unknown or weak criteria, new evidence is extracted (same quote rules), and the scorer re-runs. Max 3 loops; stops early if a loop adds nothing. Exhausted → `HOLD` (40–59) / `GO` with `LOW_CONFIDENCE` (≥ 60) / `NO_GO` (< 40). Every loop is logged in `research_steps`. |
| 4 | Context | Hunter.io (or manual CSV) | **Find the right PoC** | GO companies only. Hunter Domain Search (`type=personal`). Code ranks contacts by persona tier (security/compliance leader → engineering/IT leader → founder/CEO, with founder first when headcount < 80), eligibility (confidence ≥ 70, not `invalid`) and tie-breaks (ICP_SPEC §6). Optional Hunter Email Verifier on the chosen email. Option B: `data/manual_poc.csv` from Apollo overrides Hunter for listed domains. No eligible contact → `HOLD` with `NO_POC`. |
| 5 | AI | Pain ranker (code) + Gemini (rationale) | **Identify the 2 most likely pain points** | Code derives signals from facts and scores the fixed pain library (ICP_SPEC §7) for the PoC's persona; top 2 win (tie-break: library order). Gemini writes a 1–2 sentence person-specific rationale for each, citing evidence ids. Rationale numbers and facts are checked against evidence. |
| 6 | AI | Gemini (writer) + Gemini (critic) | **Draft the personalised email** | Gemini drafts subject + body addressed to the PoC by first name, with a hook from one evidence item (priority: news ≤ 90 days → hiring signal → security page → customers), one pain point, one Sprinto proof point from `SPRINTO_CONTEXT.md` and one soft CTA (ICP_SPEC §8). Code validator runs; the critic scores 1–5 against the rubric. Fail → one rewrite with the feedback → still failing → flagged. |
| G | Output | Review gate (GL + code) | **GL reviews** | One queue, "Needs GL" first. Each card shows: verdict + score trace, evidence list with links, why this PoC (ranked list), the 2 pain points, the draft with the hook highlighted and validator/critic results. **Approve / Edit / Reject** (edit and reject need a reason category). In `auto` mode, unflagged drafts with critic ≥ 4 skip the queue (only allowed while `to:` is our own inbox). Edit ratio is stored. |
| 7 | Output | Gmail API | **Send the email** | Sends via Gmail API (`users.messages.send`, OAuth `gmail.send` scope) from the GL's account. **`to:` is hardcoded to `DEMO_RECIPIENT`**; the intended PoC is in an `X-Intended-Recipient` header and a one-line demo footer. HTML part carries a 1×1 tracking pixel. Idempotent per (run, company). Stores the Gmail message and thread ids. |
| M | Measure | Supabase + Runs screen | **Track results** | Open events from the pixel endpoint, GL edit ratio, reply mark, time and cost per company, qualification agreement. Shown per run and as a weekly roll-up. Read-only: nothing changes the ICP automatically. |

## Data flow

`domains → pages (raw markdown) → evidence + company_facts → qualification (+ research_steps) → contacts (ranked) → pain_points → drafts (+ validator, critic) → reviews → sends → email_events`

Each arrow is a row written to Supabase, so any company can be resumed from its last completed stage and every decision can be traced back to a source URL.

## Human checkpoints (from the nine checks)
- **Gate G is the only human checkpoint**, and it sits right before the irreversible step. Nothing is sent to anyone other than `DEMO_RECIPIENT`, ever, in this build.
- **Step 3 decides with code, explores with AI.** The agent can fetch more information but can't change a score or a threshold.
- **Steps 4 and 5 rank with code.** "Why this person" and "why these pains" are rule traces, not LLM opinions.
- **Step 6 writes, it doesn't assert.** Every fact in the email must trace to evidence or SPRINTO_CONTEXT, or the draft is blocked.
- **Step 7 has no AI in it.**
